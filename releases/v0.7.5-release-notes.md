# dosforge v0.7.5

Two changes:

1. **Install layout redesigned** — flat (pipx-style) instead of
   versioned, with automatic migration from older layouts.
2. **TUI dropdown toggle fix** — clicking an expanded dropdown a
   second time now correctly closes it.

## Install layout

### Before v0.7.5

```
~/.local/share/dosforge/
├── 0.7.3/venv/      (leftover from previous install)
├── 0.7.4/venv/      (current — pointed to by `current` symlink)
├── current -> 0.7.4
└── dosassets/
```

Every upgrade left an orphaned `<version>/venv/` directory (~250 MB
each), accumulating forever.  Disk leak.

### v0.7.5 and forward

```
~/.local/share/dosforge/
├── venv/            (Python env — REPLACED on every upgrade)
├── bundle/          (extracted release contents — REPLACED on upgrade)
└── dosassets/       (USER DATA — NEVER touched on upgrade)
    ├── compaq2/Microsoft MS-DOS 2.11 [Compaq OEM]...7z
    ├── msdos622/Microsoft MS-DOS 6.22 Plus Enhanced Tools...7z
    └── ...
```

The v0.7.5 installer **auto-detects + cleans up** old versioned
directories left behind by v0.7.3 / v0.7.4 installs.  Just re-run
the installer:

```bash
curl -fsSL https://raw.githubusercontent.com/flynnsbit/dosforge/main/scripts/install.sh | bash
```

Output:
```
==> Removing legacy install: /home/you/.local/share/dosforge/0.7.3/
==> Removing legacy install: /home/you/.local/share/dosforge/0.7.4/
==> Cleaned up 2 legacy version director(ies).
==> Upgrading dosforge 0.7.4 -> 0.7.5.
```

Your `dosassets/` folder is untouched — same install media, same
`init-assets` skeleton, same `dosforge where-assets` resolution
order.

### Why the redesign

User asked: "should the install root have the version in it? what
if people upgrade, does the old version folder go away?"  Answer:
no — versioned install dirs leaked disk on every upgrade.  The
v0.7.3/v0.7.4 layout was a misguided "multi-version coexistence"
attempt that turned into pure disk waste.  pipx-style flat layout
is the standard for CLI Python tools and matches user
expectations.

## TUI dropdown toggle fix

When clicking a SingleClickSelect dropdown that was already open,
the dropdown stayed open — there was no way to close it by clicking
the chevron again.  Background: v0.6.x's `SingleClickSelect`
suppressed the parent `Select`'s Toggle handler with
`prevent_default()` to avoid a race condition between MouseDown
(which opens eagerly) and the synthesized Click (which would close
immediately afterwards).  But the suppression was unconditional,
so clicking the dropdown's chevron a second time was also
swallowed and the menu could never be closed via click.

Fix: track whether the current Toggle was caused by our own
MouseDown.  If so, suppress the parent (avoid the race).
Otherwise, let the parent run so the dropdown closes normally.

```python
class SingleClickSelect(Select):
    _just_opened_on_mouse_down: bool = False

    def _on_mouse_down(self, event) -> None:
        if not self.expanded:
            self.action_show_overlay()
            self._just_opened_on_mouse_down = True

    @_textual_on(SelectCurrent.Toggle)
    def _single_click_toggle(self, event):
        if self._just_opened_on_mouse_down:
            self._just_opened_on_mouse_down = False
            event.stop(); event.prevent_default()
            return
        # Already-open dropdown -- let parent Toggle close it.
```

Affects every dropdown in the TUI (boot mode, controller, format,
floppy type, BIOS drive type, machine target, freedos source,
ibm-dos-version, dos-install-profile, etc.).  Escape still closes
dropdowns too (Textual default).
