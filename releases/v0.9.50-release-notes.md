# dosforge 0.9.50 — release-artifact version stamp fix

Tiny housekeeping release on top of v0.9.49.

## What's wrong with v0.9.49

The v0.9.49 GitHub release page accidentally attached
`dosforge-0.9.48-py3-none-any.whl` and `dosforge-0.9.48.tar.gz`
instead of the matching 0.9.49 sdist + wheel.  The Linux
tarball (`dosforge-0.9.49-linux.tar.gz`) and Windows zips
(`dosforge-0.9.49-windows-x64.zip` and
`dosforge-0.9.49-cli-windows-x64.zip`) are correct and contain
the full v0.9.49 feature set.

Root cause: the v0.9.49 commit (`f59321c`) accidentally
excluded the `pyproject.toml` + `src/dosforge/__init__.py`
version bump from `0.9.48` → `0.9.49`, so the
`python -m build` step in CI stamped the sdist + wheel as
`0.9.48`.

## What's in 0.9.50

**Nothing new functionally** — same code as v0.9.49 (which
itself was MartyPC-Xebec FAT12 auto-default polish on top of
v0.9.48's MartyPC compatibility expansion).

Only changes:

- `pyproject.toml` version → `0.9.50`
- `src/dosforge/__init__.py` `__version__` → `0.9.50`

## Verification

After CI publishes:

- `dosforge-0.9.50-py3-none-any.whl` and
  `dosforge-0.9.50.tar.gz` should both appear on
  <https://github.com/flynnsbit/dosforge/releases/tag/v0.9.50>.
- Linux tarball + Windows zips will be identical in feature set
  to v0.9.49 (no functional code changes between the tags).

If you're already running v0.9.49 from the Linux tarball or
Windows zip, you do **not** need to upgrade — the user-facing
code is byte-equivalent.  Only upgrade if you installed via
`pip install dosforge==0.9.49` (or equivalent) and want the
package version string to match the release tag.
