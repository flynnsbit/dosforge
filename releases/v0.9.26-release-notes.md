# dosforge v0.9.26

## `dosforge grow` is real (v1 implementation)

The v0.9.22 API contract is no longer a stub: `dosforge grow` now
actually grows VHDs end-to-end on Windows and Linux.

### Pipeline

For each grow request:

1. **Snapshot** the existing VHD (MBR + first partition BPB) using
   a pure-Python reader.  Detects FAT12 / FAT16 / FAT32 correctly
   from BPB fields (Microsoft canonical algorithm: read
   `sectors_per_fat_16` first, only fall through to
   `sectors_per_fat_32` when it's zero -- otherwise you mis-read
   the volume-serial bytes as a 4-byte sectors-per-fat).
2. **Validate cluster-band match** -- refuses grows that would
   force `mformat` to pick a different cluster size (e.g. FAT16
   128 MiB → 256 MiB crosses 2 KiB → 4 KiB).  v1 can't relay out
   cluster chains across band boundaries.
3. **Extract** every file from the old partition root to a host
   scratch directory using `mcopy -s -m -n` (recursive + preserve
   mtime + overwrite).
4. **Build a fresh empty bootable VHD** at the new size via the
   existing `DiskManager.create_and_prepare` pipeline.  Same boot
   mode + filesystem format as the original, so the new VHD gets
   the same authentic bootstrap (FORMAT C: /S + system file install
   for MS-DOS family, FreeDOS bootloader for FreeDOS).
5. **Re-inject** the extracted user files via `mcopy -o -m`,
   skipping protected root-level system files (IO.SYS, MSDOS.SYS,
   IBMBIO.COM, IBMDOS.COM, COMMAND.COM, KERNEL.SYS, VHDMK.OK) so
   the fresh VHD's authentic bootstrap stays intact.
6. **Stage** every `manifest.staging_sources` entry into its
   target DOS path via `mmd` + `mcopy -o`.
7. **Atomic swap**: rename the original VHD to `<target>.bak`
   (when `keep_backup` is True, default), copy the new VHD into
   place.

### Verified scenarios (Windows)

| Boot mode | Format | Grow | Time | Result |
|---|---|---|---|---|
| `msdos622` | FAT16 | 32 M → 128 M | 9 s | ✅ IO.SYS / MSDOS.SYS / COMMAND.COM preserved, `C:\GAMES` staged with nested `DOOM/DOOM.WAD` |
| `freedos` | FAT32 | 1 G → 2 G | 22 s | ✅ KERNEL.SYS / FDCONFIG.SYS / FDOS\ all preserved, `C:\GAMES` staged, 35 curated `C:\FDOS\BIN\` files intact |

### CLI

```bash
dosforge grow \
  --target /path/to/existing.vhd \
  --new-size 2G \
  --boot-mode msdos622 \
  --add-from /tmp/exodos-staging/games=C:\\GAMES
```

Or JSON manifest:

```bash
dosforge grow --manifest plan.json
```

Both forms still validate via `validate_grow_request` before
touching disk.  Cluster-band crossings produce an actionable error:

```
Grow target (268435456 bytes) requires a 4096-byte cluster size,
but the existing VHD uses 2048-byte clusters.  dosforge grow v1
cannot relay out cluster chains across band boundaries -- pick a
target size within the same band, or use 'dosforge create' to
rebuild from scratch.
```

### v1 limitations (tracked for v2)

These don't affect the four supported boot modes' baseline
bootability but matter for power users who customized internals:

- **Custom MBR / VBR boot code is replaced** with dosforge's
  standard bootstrap for the chosen mode.  All four supported
  modes (COMPAQ331 / MSDOS622 / MSDOS71 / FREEDOS) get the same
  authentic boot setup they originally received, so 99% of users
  observe no difference.
- **IO.SYS cluster-2 contiguity** isn't explicitly enforced
  (the fresh VHD's `FORMAT C: /S` step guarantees it; FreeDOS's
  KERNEL.SYS reads via FAT chain so doesn't care).
- **Headless QEMU boot probing** (`manifest.boot_probe`) is
  accepted but not yet wired.

### Bug discovered and fixed during implementation

The naive "always read sectors_per_fat at offset 36" approach
misidentifies FAT16 disks as FAT12 because offset 36-40 on a
FAT16 VBR holds drive number / NT reserved / boot signature /
volume serial bytes (which decode as a large bogus uint32 for
"sectors per FAT").  Snapshot now follows Microsoft's spec:
sectors_per_fat_16 (offset 22) first; sectors_per_fat_32 (offset
36) only when sectors_per_fat_16 is zero.
