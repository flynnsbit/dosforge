# dosforge v0.9.3

Bug fix release.  Despite v0.9.2's destination + URL fixes,
FreeDOS auto-fetch builds were *still* hanging at "Verifying DMI
Pool Data..." with a blinking cursor in 86Box.  Direct hex-dump
inspection of the produced VHDs identified two compounding
regressions in the boot-record write path.

## Issue 1: FAT32 silent FAT16-on-FAT32 boot sector swap

The "Fetch latest FreeDOS" flow ran `_write_fat32_boot_template`
to seed `BOOTSECT_FAT32.BIN`.  Without a local reference FreeDOS
VHD on the host (the normal case on a clean install), the helper
fell through to `mkfs.fat -F 32 -C fat32-template.img` and copied
the first 512 bytes of the resulting file.  But mkfs.fat's first
512 bytes are a *"This is not a bootable disk"* stub with OEM
string `mkfs.fat`, not a real FreeDOS boot sector.

When dosforge later resolved the FreeDOS asset dir,
`_looks_like_freedos_fat32_boot_sector` (which requires
`FRDOS5.1` + `KERNEL  SYS` in the sector) correctly rejected the
mkfs stub.  But the fallback path in `_resolve_freedos_from_
directory` then silently substituted `BOOTSECT_FAT16.BIN` --
a FAT16 boot sector with jmp opcode `EB 3C 90` and FAT16 BPB
layout -- onto a FAT32 partition.  The FAT32 BPB region
(offsets 36-89) overlaps the FAT16 boot code start area, the
jmp landed in BPB data, and the CPU jumped into garbage:
blinking cursor.

### Fix

Added `_BUILTIN_FAT32_BOOT_SECTOR_B64`, a base64-encoded copy of
the bundled `dosassets/freedos/BOOTSECT_FAT32.BIN` (real FreeDOS
boot32lb, OEM `FRDOS5.1`, jmp `EB 58 90`).  `_write_fat32_boot_
template` now seeds this builtin between the local-VHD search
and the mkfs.fat last-resort fallback, so a clean install always
produces a real bootable FreeDOS FAT32 sector.

The mkfs.fat fallback is retained as a defense-in-depth final
resort but should never fire on shipped builds.

## Issue 2: 71-byte CHS-only MBR breaks 86Box boots

Inspecting the produced VHDs against a known-good v0.6-era build
revealed the MBR boot code had regressed from a 430-byte syslinux
LBA-aware MBR to a 71-byte CHS-only stub.  The stub uses INT 13h
AH=02h CHS reads, which fail on 86Box (and other emulators) when
the BIOS-presented HDD geometry diverges from the partition
table's CHS encoding -- the read targets the wrong sector, the
"VBR has bad signature" check fails, and the MBR drops to INT 18h
("ROM BASIC") leaving the blinking cursor after the post.

Root cause: `_seed_builtin_fat16_boot_records` always wrote
`_BUILTIN_MSDOS_MBR_BOOT_CODE_B64` (the 71-byte stub) to the
cache without checking for a better MBR on the host first.
`_apply_freedos_reference_boot_records` then set
`assets.mbr_boot_code_template` to the cached file, which bypassed
`BootInstaller._find_mbr_boot_code` (which would have picked
`/usr/lib/syslinux/bios/mbr.bin` -- a 412-byte LBA-aware MBR
shipped by the `syslinux` package and present on every Arch /
Debian host).

### Fix

1.  `_seed_builtin_fat16_boot_records` now calls a new helper,
    `_resolve_fat16_mbr_boot_code_bytes`, which iterates
    `DEFAULT_MBR_BOOT_CODE_CANDIDATES` (the syslinux mbr.bin
    locations) and uses the first one that exists and is at
    least 440 bytes of valid boot code.  The 71-byte builtin
    becomes a last-resort fallback for Windows hosts (and the
    rare Linux host without syslinux installed).

2.  `_load_cached_fat16_boot_record_paths` now detects when an
    existing cached MBR matches the builtin byte-for-byte AND
    a syslinux source is now available -- in that case it
    returns `None`, forcing
    `_apply_freedos_reference_boot_records` to re-seed from the
    syslinux MBR.  Existing users get the fix transparently on
    their next build; no manual cache wipe required.

## Migration

No user action required.

- Issue 1: the next "Fetch latest FreeDOS" pass overwrites the
  stub `BOOTSECT_FAT32.BIN` because the existing-file check
  routes the stub through the same `_looks_like_freedos_fat32_
  boot_sector` validator that rejected it in the first place.
- Issue 2: the cache-invalidation check in
  `_load_cached_fat16_boot_record_paths` detects the stale
  71-byte cached MBR on the next build and re-seeds from
  syslinux automatically.

If you still see "Verifying DMI Pool Data..." after upgrading,
wipe both stale artifacts manually:

```bash
rm -f ~/.local/state/dosforge/cache/boot-assets/fat16-native-mbr.bin
rm -f ~/.local/share/dosforge/dosassets/freedos/BOOTSECT_FAT32.BIN
dosforge gui   # or dosforge tui
# then click "Fetch latest FreeDOS assets" again
```

## Tests

- 5 focused tests pass in `tests/test_boot_assets.py`:
  - `test_write_fat32_boot_template_prefers_local_freedos_vhd`
  - `test_write_fat32_boot_template_seeds_builtin_when_no_local_source` *(new)*
  - `test_seed_builtin_fat16_boot_records_prefers_syslinux_mbr` *(new)*
  - `test_seed_builtin_fat16_boot_records_falls_back_to_builtin_without_syslinux` *(new)*
  - `test_load_cached_fat16_boot_records_invalidates_stale_builtin` *(new)*

## Files changed

- `src/dosforge/boot.py`
  - new constant `_BUILTIN_FAT32_BOOT_SECTOR_B64` (real FreeDOS
    boot32lb, OEM `FRDOS5.1`, jmp `EB 58 90`).
  - `_write_fat32_boot_template`: builtin seeded between the
    local-VHD search and the mkfs.fat last-resort fallback.
  - `_seed_builtin_fat16_boot_records`: now delegates to a new
    `_resolve_fat16_mbr_boot_code_bytes` helper that prefers
    `DEFAULT_MBR_BOOT_CODE_CANDIDATES` (syslinux mbr.bin) over
    the 71-byte embedded stub.
  - `_load_cached_fat16_boot_record_paths`: rejects stale cached
    71-byte builtin when a syslinux source is now available, so
    existing users get the fix without manual cache cleanup.

- `tests/test_boot_assets.py`: four new regression tests cover
  both code paths (with-syslinux, without-syslinux, stale-cache
  invalidation, FAT32 builtin fallback).

## Not changed

- All other boot-mode flows.
- `--freedos-download-url` CLI flag still overrides the pinned
  default if the user wants to test a newer FreeDOS revision.
- The FreeDOS auto-fetch pin from v0.9.2
  (`330e522bf9323ad54a6ff68c9b7cb9ae7a084cb4`) is unchanged.
