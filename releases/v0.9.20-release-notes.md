# dosforge v0.9.20

## Fix: DR-DOS 6 / DR-DOS 7 VHD install actually runs FORMAT now

v0.9.10 claimed to wire the DR-DOS 6/7 VHD install pipeline, but the
generated `AUTOEXEC.BAT` ran `FORMAT C:` (no extra flags) which
DR-DOS R2.0 `FORMAT.COM` always rejects with:

```
Option /X must be specified when formatting a fixed disk
```

Since the AUTOEXEC had no `IF ERRORLEVEL` check, the install marched
forward, the subsequent `SYS C:` step failed with *"Non-standard
sector length - cannot write new boot sector"* (because the partition
was never formatted), and the build eventually timed out with the
misleading "did not write `C:\VHDMK.OK`" error.

The disk we built ended up with a completely empty partition (no BPB,
no boot signature). The two prior v0.9.x attempts (UX gate v0.9.18,
WHPX/timeout v0.9.19) were both treating the symptom; this release
fixes the actual cause.

### Changes

- **`LegacyDosInstallProfile.format_extra_args`** — new bytes field
  appended to `FORMAT C:` in both `use_sys_after_format` (DR-DOS) and
  classic `format` paths. Empty by default; preserves existing
  MS-DOS / PC-DOS / Compaq behavior byte-for-byte.
- **`drdos6_profile` / `drdos7_profile`** — set
  `format_extra_args=b" /X"` and updated `format_yes_input` to
  `b"Y\r\n\r\n\r\n"` (Y for the documented *"Proceed with format
  (Y/N)?"* prompt, ENTER for the empty volume label, plus a buffer
  ENTER).

### Files changed

- `src/dosforge/legacy_dos_install.py` (one new field, both DR-DOS
  profile builders updated, AUTOEXEC generator threads
  `profile.format_extra_args` into the `FORMAT C:` line)
- `pyproject.toml` + `src/dosforge/__init__.py` (0.9.19 → 0.9.20)

### Verification

The fix is symmetric across Linux and Windows because
`FORMAT.COM` is byte-identical inside the install floppy in both
platforms — the same DR-DOS R2.0 `FORMAT.COM` ran inside QEMU and
required `/X` on both hosts. Re-runs of the DR-DOS 6 build now
exercise the full FORMAT → SYS → marker → COPY sequence.

The smoke matrix `_KNOWN_BROKEN` table for DR-DOS 6/7 VHD was
cleared by v0.9.10 prematurely; with this release the cases should
genuinely pass.

### Carried forward

- v0.9.19's WHPX accel + 3× Windows timeout multiplier are still
  active; they're harmless safety nets even though the underlying
  failure was never about cycles.
- v0.9.17's graceful `mdeltree` fallback remains in place.
