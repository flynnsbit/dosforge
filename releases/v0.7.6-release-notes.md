# dosforge v0.7.6 — installer cleanup

Hot-fix for `scripts/install.sh` shipped in v0.7.5.

## Bug

User noticed two `dosassets/` folders after installing:

```
~/.local/share/dosforge/
├── bundle/
│   └── dosassets/    ← duplicate, unused, confusing
└── dosassets/        ← the real one, user-data
```

The release tarball ships a `dosassets/` skeleton at its root so the
"extract the tarball and `cd` into it" workflow has install media
folders ready out of the box.  Our flat installer hydrates a
separate top-level `<prefix>/dosassets/` via `init-assets --target`
(so upgrades don't touch user data), which makes the bundled
skeleton dead weight + confusing.

## Fix

`install.sh` now removes `bundle/dosassets/` after extracting the
tarball:

```
==> Extracting bundle...
==> Removed duplicate /home/you/.local/share/dosforge/bundle/dosassets/
    (real one lives at /home/you/.local/share/dosforge/dosassets/).
```

And the `migrate_legacy_layout()` helper also cleans up the
duplicate from previous v0.7.5 installs, so users who just re-run
the installer get a clean state without manually deleting anything.

## Re-running the installer

```bash
curl -fsSL https://raw.githubusercontent.com/flynnsbit/dosforge/main/scripts/install.sh | bash
```

Output on a v0.7.5 -> v0.7.6 upgrade:
```
==> Removed duplicate bundle/dosassets/ from previous install.
==> Upgrading dosforge 0.7.5 -> 0.7.6.
```

## Files changed

- `scripts/install.sh`: removes `bundle/dosassets/` after extracting
  the tarball; `migrate_legacy_layout()` also cleans up the
  duplicate from existing v0.7.5 installs
- `pyproject.toml` + `src/dosforge/__init__.py`: 0.7.5 -> 0.7.6
- `releases/v0.7.6-release-notes.md`: this file

## Compatibility

100% behavior-compatible with v0.7.5.  Pure installer cleanup.
