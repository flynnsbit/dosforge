# dosforge v0.9.37

## Fix FreeDOS FAT32 boot for VHDs > 503 MiB (Grow + Create)

User-reported regression in v0.9.36: growing a FreeDOS FAT32 VHD
from 32 MiB to 512 MiB succeeded all the way through the rebuild
+ inject pipeline, but the freshly built VHD silently failed the
headless boot probe (empty serial log → 90s timeout → grow aborted
with "Boot probe failed" and the original VHD left untouched).

### Root cause

The MBR partition entry's **end-CHS** triplet was being encoded as
`0xFE / 0xFF / 0xFF` for any partition whose end LBA exceeded the
24-bit CHS reach (cylinder > 1023).  On a 16-head / 63-spt VHD that
threshold is ~503 MiB, so every FAT32 VHD >504 MiB hit this code
path — including the user's 512 MiB grow target.

`0xFE / 0xFF / 0xFF` is Microsoft's canonical "use LBA" marker.  The
MS-DOS MBR boot loader (which dosforge installs at sector 0 to chain
to the FreeDOS partition VBR) treats that marker as a signal to
switch from `INT 13h AH=02` (CHS read) to `INT 13h AH=42`
(Extended/LBA read).  But the IDE / floppy controller configurations
dosforge passes to headless QEMU and 86Box's AUTO IDE do not always
honour `AH=42` against the C: drive at MBR-chain time — the BIOS
returns an error and the VBR is never loaded.  No DOS code ever
runs, so the serial log stays empty.

This is **not** a new bug introduced by Grow; it was lurking in
every `dosforge create` for FreeDOS FAT32 ≥ ~505 MiB.  Grow just
exposed it more broadly because growing past 503 MiB is a normal
target size for users coming from a 32 MiB seed VHD.

### Fix

`_lba_to_chs` in `src/dosforge/_core/mbr.py` now **clamps** to
`(1023, heads − 1, spt)` — the maximum CHS representable for the
disk's actual geometry — instead of emitting the `0xFE FF FF` LBA
marker.  This keeps the MBR boot loader on `INT 13h AH=02` for the
VBR-chain read at LBA 63 (always safely within CHS reach) and lets
FreeDOS `boot32lb` take over with its own BPB-driven LBA logic to
load `KERNEL.SYS` from anywhere on the disk.

The clamp affects only the MBR partition entry's end-CHS encoding;
the partition's `first_lba` / `sector_count` are unchanged and DOS
still sees the full partition size from the BPB's `total_sec_32`.

### Verification

Headless QEMU boot probe (i486, 16 MiB RAM, IDE) against freshly
created VHDs:

| Size | spc | end_chs before | end_chs after | probe |
|------|-----|---------------|---------------|-------|
| 256 MiB | 1 | `0fbf08` | `0fbf08` | OK both |
| 500 MiB | 8 | `0ffff7` | `0ffff7` | OK both |
| 510 MiB | 8 | `feffff` | `0fffff` | FAIL → **OK** |
| 512 MiB | 8 | `feffff` | `0fffff` | FAIL → **OK** |
| 1024 MiB | 8 | `feffff` | `0fffff` | FAIL → **OK** |

User's exact grow scenario (`/home/shawn/.local/share/86Box/Virtual
Machines/dosforge-smoke/v0.9.30/freedos-32M-FAT32.VHD` → 512 MiB)
now completes end-to-end in **2.4 s** including boot probe, instead
of aborting after 90 s.
