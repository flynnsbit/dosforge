# dosforge v0.8.2

UI now enforces the FAT-format size cap (FAT12=32 MiB, FAT16=2 GiB,
FAT32=2 TiB) for **every** boot mode, not just the ones with an
explicit per-mode cap.  Closes a gap where FreeDOS / MSDOS622 /
MSDOS71 / PCDOS71 etc. let you type any size and only surfaced the
"FAT16 DOS-compatible images must not exceed 2 GiB" error at the
moment you clicked **Create**.

## The gap (v0.8.1 and earlier)

For boot modes WITHOUT a `max_mb` in their per-boot-mode rule,
the snap chain and `validate_media_step` did nothing -- the user
could pick FreeDOS, FAT16, and type "5G" without warning until
they hit Create.

| Boot mode | Per-mode `max_mb` | Result before v0.8.2 |
|---|---|---|
| FreeDOS, MSDOS622, MSDOS71, PCDOS71, MSDOS5, MSDOS6, MSDOS331, COMPAQ331, PCDOS, PCDOS7, PCDOS2000 | _(none)_ | UI accepted 5G FAT16; failed at Create. |
| IBM8088, MSDOS33 | 32 MiB | UI clamped to 32 MiB. |
| COMPAQ2, PCDOS3, COMPAQ3 | 16 MiB | UI clamped to 16 MiB. |
| DRDOS6 | 32 MiB | UI clamped to 32 MiB. |
| DRDOS7 | 2 GiB | UI clamped to 2 GiB. |

## v0.8.2 fix

Added a `_FAT_FORMAT_MAX_MB` table + `_effective_max_mb(rule, fmt)`
helper that returns the **tighter** of:

- the per-boot-mode `max_mb` (if any), and
- the FAT format's natural cap (FAT12=32 MiB, FAT16=2 GiB,
  FAT32=2 TiB).

This cap now flows through three places:

1. **`_snap_size_for_boot_mode`** — when the user picks a new boot
   mode or filesystem, the size Input auto-clamps to the effective
   cap. E.g. switching from FREEDOS+FAT32+10G to FREEDOS+FAT16
   now snaps the size to **2G** instead of leaving 10G stuck.
2. **`validate_media_step`** (Step 2 → Step 3 "Next" click) —
   rejects oversized values with a clear "fat16 partitions cannot
   exceed 2G (the FAT format's hard cap)" message *before* the user
   advances to Step 3.
3. **`geometry_preview_text`** (live preview Label) — adds the cap
   to the preview suffix, e.g.

   ```
   -> 1024 MB (geometry auto-derived from size) (max 2G for fat16)
   ```

   so the user sees the ceiling at a glance, not only when they
   accidentally cross it.

## What didn't change

- `CreateRequest` API, CLI flags, backend `validate_size_for_format`
  (kept as a defense-in-depth final check).
- Boot modes with explicit per-mode caps still enforce their
  tighter limit (e.g. IBM8088 FAT16 stays at 32 MiB, not 2 GiB).
- FAT12 modes — already correctly capped at 32 MiB.
- Tests asserting the existing per-mode caps continue to pass.

## Tests

182/182 focused tests pass — 6 new tests cover:
- FreeDOS FAT16 5G → 2G clamp
- MSDOS622 FAT16 4G → 2G clamp
- IBM8088 FAT16 500M → 32M (tighter per-mode cap wins)
- FreeDOS FAT32 5T → 2 TiB clamp
- `validate_media_step` rejects 3G FAT16 on FreeDOS
- preview line includes "max 2G for fat16" suffix

  `validate_media_step` + `geometry_preview_text` rewired.
- `tests/test_formlogic.py` — 6 new test cases.
