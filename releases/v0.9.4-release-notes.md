# dosforge v0.9.4

Bug fix release.  v0.9.3 fixed the FreeDOS FAT16 "Verifying DMI
Pool Data..." hang in 86Box but the FAT32 variant kept hanging.
The actual cause was deeper than the boot-record-write path.

## Issue: FreeDOS FAT32 boot sector required INT 13h Extensions

The boot sector dosforge shipped as `BOOTSECT_FAT32.BIN` was
built from FreeDOS `kernel/boot/boot32lb.asm` -- the *LBA*
variant.  boot32lb uses `INT 13h AH=42h` (extended read) to
load `KERNEL.SYS`.

INT 13h Extensions are universal on real hardware, modern QEMU
SeaBIOS, and most 86Box machine profiles -- so the FAT32 builds
booted cleanly in QEMU all along.  But some legitimate emulated
BIOSes don't expose them:

- 86Box's Award FIC VA-503+ (Pentium MMX) BIOS, the most common
  "modern AT" profile in dosforge-smoke, does not return success
  for the `INT 13h AH=41h` extension-installation check on the
  IDE hard disk that 86Box presents.
- The user's empirical result confirmed it: same 86Box config,
  FAT16 (CHS reads, no LBA) boots fine; FAT32 (LBA reads)
  hangs at "Verifying DMI Pool Data..." with a blinking cursor.
- A separate sanity check confirmed the Windows 98 OSR2 FAT32
  boot sector (which uses CHS reads only) boots fine on the
  exact same machine -- isolating the failure to boot32lb's
  LBA dependency, not a structural problem with dosforge's
  partition / FAT / MBR layout.

### Fix

Replaced the bundled `dosassets/freedos/BOOTSECT_FAT32.BIN`
(and the embedded `_BUILTIN_FAT32_BOOT_SECTOR_B64` constant
that is its base64 form) with FreeDOS `kernel/boot/boot32.asm`
(the CHS variant), assembled via NASM 3.01.

boot32 uses `INT 13h AH=02h` (CHS read) which every PC BIOS
since 1983 supports.  All FAT32 partitions dosforge produces
are well under the 8 GiB CHS limit (typical sizes 64 MiB - 2
GiB), so the CHS variant works everywhere the LBA variant did
*plus* the older BIOSes the LBA variant didn't.

The boot sector still validates as FreeDOS via
`_looks_like_freedos_fat32_boot_sector` because we keep the
`FRDOS5.1` OEM stamp at offset 3 and the `KERNEL  SYS`
filename marker at offset 497.

## Migration

No user action required:

- The bundled `BOOTSECT_FAT32.BIN` is shipped in this release.
- An installed dosassets dir (typically
  `~/.local/share/dosforge/dosassets/freedos/`) still contains
  the v0.9.3 LBA `BOOTSECT_FAT32.BIN` from the previous fetch,
  but the file is timestamped older than the install; the next
  `Fetch latest FreeDOS` re-seeds it from the new builtin via
  `_write_fat32_boot_template`.
- VHDs already produced with v0.9.3 (LBA boot code on disk) can
  be re-patched in place by re-running the build with
  `--overwrite`, since the boot-write step replaces only the
  jmp + boot code + sig (offsets 0..2, 90..510) while preserving
  the mkfs.fat BPB.

If you've already created FAT32 VHDs with v0.9.3 and want them
to boot on 86Box without rebuilding, you can drop the new
`BOOTSECT_FAT32.BIN` into the partition manually -- but
rebuilding is simpler.

## Tests

5 focused tests pass in `tests/test_boot_assets.py`:
- `test_write_fat32_boot_template_prefers_local_freedos_vhd`
- `test_write_fat32_boot_template_seeds_builtin_when_no_local_source`
- `test_seed_builtin_fat16_boot_records_prefers_syslinux_mbr`
- `test_seed_builtin_fat16_boot_records_falls_back_to_builtin_without_syslinux`
- `test_load_cached_fat16_boot_records_invalidates_stale_builtin`

The first two cover the new CHS boot sector contents (size,
jmp opcode `EB 58 90`, OEM `FRDOS5.1`, signature, `KERNEL  SYS`
marker) -- they pass with both LBA and CHS variants because
those structural fields are identical.

End-to-end boot verified in QEMU SeaBIOS (`qemu-system-i386`)
with the CHS-patched VHD reaching the FreeCOM `C:\>` prompt.

## Files changed

- `dosassets/freedos/BOOTSECT_FAT32.BIN`: replaced LBA variant
  with CHS variant (assembled from boot32.asm + FRDOS5.1 OEM
  stamp).  Still 512 bytes, same jmp opcode `EB 58 90`, same
  KERNEL.SYS filename embedded at offset 497.

- `src/dosforge/boot.py`:
  - `_BUILTIN_FAT32_BOOT_SECTOR_B64`: re-encoded to match the
    new CHS-variant bundled file (identical bytes).
  - Comment updated to document why CHS is preferred over LBA
    and which BIOS profiles need it.

## Not changed

- The FAT16 boot path is unchanged from v0.9.3.
- The syslinux LBA-aware MBR fix from v0.9.3 still applies (it
  loads the FAT32 partition's first sector once, then transfers
  control -- and the partition load itself uses CHS at MBR time,
  so 86Box's missing INT 13h Extensions for the IDE disk doesn't
  trip it).
- All other boot-mode flows.
- The FreeDOS auto-fetch pin from v0.9.2
  (`330e522bf9323ad54a6ff68c9b7cb9ae7a084cb4`) is unchanged.
