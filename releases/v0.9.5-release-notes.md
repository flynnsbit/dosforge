# dosforge v0.9.5

Removes a stale validation gate that survived from v0.8.3 and
predates the v0.9.3 + v0.9.4 FreeDOS FAT32 fixes.

## What v0.8.3 used to gate, and why it can go

Back in v0.8.3 the bundled `dosassets/freedos/` only contained
FAT16 boot assets.  Picking FreeDOS + AUTO + FAT32 would have
produced an unbootable VHD, so v0.8.3 added an upfront
`ValidationError` ("FreeDOS auto-download boot mode currently
supports FAT16 only.  For FAT32, use local FreeDOS assets with
BOOTSECT_FAT32.BIN.") and a matching footer hint in the TUI/GUI.

v0.9.3 then shipped a bundled `BOOTSECT_FAT32.BIN` + an embedded
`_BUILTIN_FAT32_BOOT_SECTOR_B64` fallback that
`_write_fat32_boot_template` seeds when no host-side reference
VHD exists.  v0.9.4 rebuilt that bundled boot sector from
FreeDOS `boot32.asm` (CHS) instead of `boot32lb.asm` (LBA) so
it boots on any BIOS.

The AUTO-source code path was never updated, so:
- `validate_media_step` in `formlogic.py` still surfaced the
  hint at "Next →" (visible in the user's v0.9.4 screenshot)
- `_validate_create_request` in `disk.py` still raised
  `ValidationError` at Create time
- `_resolve_freedos_from_image` in `boot.py` still raised
  `ValidationError` when actually resolving boot assets

This release removes all three gates and re-wires
`_resolve_freedos_from_image` to seed the FAT32 boot sector
from the bundled / built-in CHS template instead of refusing.

## Behaviour change

`dosforge create --boot-mode freedos --freedos-source auto
--format fat32 --media-type vhd ...` now succeeds.  Same goes
for the equivalent TUI / GUI flow (FreeDOS + Auto-download +
FAT32 + VHD) -- the footer hint is gone, Next proceeds without
complaint, and Create produces a bootable VHD.

The bundled CHS boot sector + the v0.9.3 syslinux LBA-aware MBR
combination is what's exercised; the produced VHD boots in
QEMU's SeaBIOS and in 86Box's Award FIC VA-503+ Pentium MMX
profile (where the earlier LBA variant hung at "Verifying DMI
Pool Data...").

## Files changed

- `src/dosforge/formlogic.py`: removed the FreeDOS-AUTO+FAT32
  branch in `validate_media_step`.
- `src/dosforge/disk.py`: removed the FreeDOS-AUTO+FAT32 branch
  in `_validate_create_request`.
- `src/dosforge/boot.py`: `_resolve_freedos_from_image` no
  longer raises for FAT32; it now seeds
  `extraction_root/BOOTSECT_FAT32.BIN` via
  `_write_fat32_boot_template` (which prefers a local FreeDOS
  reference VHD, falls back to the bundled
  `dosassets/freedos/BOOTSECT_FAT32.BIN`, then to the embedded
  `_BUILTIN_FAT32_BOOT_SECTOR_B64`).
- `tests/test_formlogic.py`: replaced
  `test_freedos_auto_fat32_rejected_at_next` with
  `test_freedos_auto_fat32_allowed` (asserts the gate is gone).
- `tests/test_disk_validation.py`: replaced
  `test_validate_rejects_freedos_auto_with_fat32` with
  `test_validate_accepts_freedos_auto_with_fat32`.

## Not changed

- Everything from v0.9.4 (CHS boot sector, FRDOS5.1 OEM,
  bundled `dosassets/freedos/BOOTSECT_FAT32.BIN`).
- The LOCAL source path is unchanged and still works.
- All non-FreeDOS boot modes.
