# dosforge v0.9.29

## `dosforge grow` v2: headless QEMU boot probe

`manifest.boot_probe` (default `True`) now actually runs.  After the
fresh VHD is built and user files are injected -- but BEFORE the
atomic swap -- dosforge headless-boots the new VHD in QEMU and
verifies it reaches AUTOEXEC.BAT.  On probe failure, the grow is
aborted and the user's original VHD stays untouched.

### How it works

1. Snapshot the new temp VHD's `AUTOEXEC.BAT` bytes (or treat as
   empty if absent).
2. Write a small `C:\BOOTPRB.BAT` to the partition:

   ```dos
   @ECHO OFF
   CTTY COM1
   ECHO DOSFORGE_BOOT_PROBE_OK
   CTTY CON
   ```

3. Prepend `@CALL C:\BOOTPRB.BAT` to AUTOEXEC.BAT (the marker fires
   before any user commands, so it works even when AUTOEXEC ends in
   `WIN` or similar blocking calls).
4. Boot the VHD in headless QEMU with serial captured to a file
   using the **`chardev` syntax** (`-chardev file,id=bplog,path=...
   -serial chardev:bplog`).  This avoids the well-known `-serial
   file:C:\path` Windows-path colon-parser bug that silently
   produces zero-byte logs.
5. Poll the serial log for `DOSFORGE_BOOT_PROBE_OK` every second,
   up to 90 seconds.  Kill QEMU once found (or on timeout).
6. **Always restore** the original AUTOEXEC.BAT (or delete it if it
   didn't exist) and delete `C:\BOOTPRB.BAT`, even on failure paths.
7. On probe success: proceed to atomic swap.
   On probe failure: raise `ValidationError` with the serial-log
   tail.  The user's original VHD is **not** modified.

### CLI

```bash
# Probe runs by default
dosforge grow --target disk.vhd --new-size 256M --boot-mode msdos622

# Skip probe (faster ~6s, useful for trusted batch flows)
dosforge grow --target disk.vhd --new-size 256M --boot-mode msdos622 --no-boot-probe
```

### Measured overhead

End-to-end Windows tests on a `msdos622` 32 MiB → 128 MiB grow:

| Probe | Total time |
|---|---|
| `--no-boot-probe` | 7.3 s |
| boot probe enabled (default) | 13.3 s |

The ~6 s overhead is the QEMU boot cycle (TCG software emulation
on Windows; WHPX-accelerated runs would be faster).

### Why this matters

The grow pipeline was already pretty safe (cluster-band validation
+ system files survived from the fresh `dosforge create` step), but
there were edge cases where user file injection could break boot:

- A user's `CONFIG.SYS` `DEVICE=` line referencing a file that the
  fresh dosforge-curated `C:\DOS\` doesn't contain (e.g.
  installer-time only files filtered out in v0.9.23).
- Mismatched OEM stamp expectations between the user's original
  boot sector and the fresh dosforge one for that boot mode.
- Corruption from interrupted writes mid-injection.

The probe catches all three of these before the atomic swap, so a
failed grow never costs the user their working VHD.
