# dosforge v0.9.2

Bug fix release.  FreeDOS auto-fetch builds were hanging at
"Verifying DMI Pool Data..." with a blinking cursor in the
emulator because of two compounding issues.

## Issue 1: `fetch_freedos_assets` wrote to the wrong directory

The "Fetch latest FreeDOS" button (and the
`DiskManager.fetch_freedos_assets()` API in general) wrote the
freshly-downloaded FreeDOS assets to `<CWD>/dosassets/freedos/`.

On an installed Linux bundle (where `DOSFORGE_DOSASSETS_DIR`
points at `~/.local/share/dosforge/dosassets/`) and a Windows
bundle (where it points at `C:\Apps\DosForge\dosassets\`), this
meant:

1. Fetch button wrote to `~/dosassets/freedos/` (your CWD).
2. Create step called `resolve_dos_asset_dir("freedos")` which
   returned the bundle path -- the stale bundled boot sectors.
3. Built VHD used the stale bundled BOOTSECT_FAT16.BIN /
   BOOTSECT_FAT32.BIN that may not match the current FreeDOS
   kernel.
4. Emulator: "Verifying DMI Pool Data...." + blinking cursor.

### Fix

`fetch_freedos_assets` now resolves the destination via the same
chain `resolve_dos_asset_dir("freedos")` reads from -- so the
fetch writes to the exact location the create step reads back.

## Issue 2: `FREEDOS_DEFAULT_IMAGE_URL` tracked `master`

The default download URL pointed at the moving `master` branch of
`codercowboy/freedosbootdisks` on raw.githubusercontent.com.
Every time upstream pushed a new commit to master, dosforge
silently fetched whatever happened to be there -- including
images with a different boot-sector / kernel layout than dosforge
expects.

### Fix

Pinned `FREEDOS_DEFAULT_IMAGE_URL` to commit
`330e522bf9323ad54a6ff68c9b7cb9ae7a084cb4` -- the same commit
already used by `FREEDOS_FALLBACK_IMAGE_URL`.  This is the known-
good revision dosforge has been verified against.  Re-pinning
when a new FreeDOS revision is validated is now a one-line edit.

## Migration

No user action required.  The fix is transparent:

- The cache key is the URL hash; the pinned URL has a different
  hash than the old `master` URL, so the next build re-downloads
  to a fresh cache entry.  Any stale `freedos-<master-hash>.img`
  in your cache stays there harmlessly (never read).
- The fresh fetch lands in the correct bundle-relative location
  this time, overwriting the stale bundled boot sectors.

If you still see "Verifying DMI Pool Data..." after upgrading,
clear the FreeDOS cache + re-fetch:

```bash
rm -rf ~/.local/state/dosforge/cache/boot-assets/freedos-*.img
rm -rf ~/.local/share/dosforge/dosassets/freedos/
dosforge gui   # or dosforge tui
# then click "Fetch latest FreeDOS assets" again
```

## Tests

191/191 focused tests pass.  The fix is a URL pin + a
destination-resolver swap; existing tests already cover the
behavior that's now reliable.

## Files changed

- `src/dosforge/boot.py` -- `FREEDOS_DEFAULT_IMAGE_URL` pinned
  to `330e522...`.
- `src/dosforge/disk.py` -- `fetch_freedos_assets` now resolves
  destination via `resolve_dos_asset_dir("freedos")` /
  `dos_assets_root()` instead of `<CWD>/dosassets/freedos`.

## Not changed

- `--freedos-download-url` CLI flag still overrides the pinned
  default if the user wants to test a newer FreeDOS revision.
- `FREEDOS_FALLBACK_IMAGE_URL` unchanged (was already pinned).
- All other boot-mode flows unchanged.
