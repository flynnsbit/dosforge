# dosforge v0.9.19

Fix the actual root cause of DR-DOS 6 (and other legacy DOS) VHD
install timeouts on Windows.  Reverts v0.9.18's UX gate -- the
install is supposed to work on Windows too, just much slower
without hypervisor acceleration.

## Root cause

`legacy_dos_install._run_qemu` launched `qemu-system-i386`
without an `-accel` flag, so QEMU defaulted to pure software
emulation (TCG).  On Linux dosforge runs against KVM-backed
QEMU which is roughly 3-5x faster than TCG, so the
profile-declared 300 s timeout was plenty.  On Windows TCG that
same install routinely needs 5-15 minutes -- the 300 s timeout
fired before `FORMAT.COM` / `SYS C:` reached the FAT scan pass,
hence the misleading "VHDMK.OK marker not written" error.

## Fix

Two targeted changes in `legacy_dos_install._run_qemu`:

1. **Enable WHPX acceleration on Windows.** Pass
   `-machine pc,accel=whpx:tcg` instead of just `-machine pc`.
   QEMU tries Windows Hypervisor Platform (WHPX) first and falls
   back to TCG when WHPX isn't installed.  WHPX is built into
   Windows 10+ and just needs the "Windows Hypervisor Platform"
   optional feature enabled (Settings -> Apps -> Optional
   features -> More Windows features).  Linux QEMU ignores the
   `whpx` accel name and uses its default (KVM/TCG), so the
   change is a no-op on Linux.

2. **3x timeout multiplier on Windows.** New
   `_effective_timeout_seconds(profile)` returns
   `profile.timeout_seconds * 3` on Windows hosts, unchanged on
   other platforms.  Safety net for users without WHPX who fall
   through to TCG -- a 300 s Linux/KVM install gets 900 s on
   Windows/TCG, enough headroom for slow DR-DOS / PC-DOS
   FORMAT runs.  WHPX-accelerated installs finish well under the
   bumped timeout and don't notice.

## Improved timeout error diagnostics

The "did not complete within" error message now includes:

- the path to the QEMU serial-output log
  (`legacydos-qemu-<hex>.log` under the cache dir) so users
  can read the full DOS console output post-mortem, and
- the path to the install floppy (preserved for verify
  failures so users can mount it and inspect `STEP.TXT` /
  `FMT_OUT.TXT` / `SYS_OUT.TXT`).

Reading the serial log is the fastest way to tell whether the
install hung at a specific FORMAT prompt or just timed out
during the slow FAT scan.

## Reverted

v0.9.18's `_KNOWN_BROKEN_VHD_BOOT_MODES` gate is removed.
DR-DOS 6/7 VHD builds were never broken on Linux; the regression
was Windows-specific and is now properly fixed.  The smoke
matrix script's `_KNOWN_BROKEN` table likely needs the same
removal but that's a script-side concern (no behaviour change in
the CLI / GUI / TUI).

## How to verify WHPX is active

After upgrading, run a DR-DOS 6 VHD build.  In QEMU verbose
output the line `whpx: API version ...` (or `whpx: Hypervisor
Platform...`) confirms WHPX is doing the heavy lifting.  If you
see `accel/tcg: ...` instead, fall back to TCG happened -- the
3x timeout multiplier covers that case.

If WHPX is not installed and you want full speed:

```
Settings -> Apps -> Optional features -> More Windows features
-> check 'Windows Hypervisor Platform' -> OK -> reboot
```

## Tests

Existing focused tests pass.  Behaviour change is gated on
`sys.platform == "win32"`; Linux + macOS hosts see identical
runtime to v0.9.17.

## Files changed

- `src/dosforge/legacy_dos_install.py` -- import `sys`;
  `_run_qemu` adds `accel=whpx:tcg` on Windows; new
  `_effective_timeout_seconds` static helper applied at the
  timeout deadline + the error message; diagnostics log path
  surfaced in the error.
