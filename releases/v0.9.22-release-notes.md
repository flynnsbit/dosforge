# dosforge v0.9.22

## New: `dosforge grow` subcommand (PREVIEW — contract frozen, implementation pending)

Introduces the public API surface for in-place VHD growth so
downstream tooling (notably `exodosconverter`) can integrate
against a stable contract while the actual rewrite pipeline is
being built.

### What works today

- **`dosforge grow --help`** documents every flag.
- **CLI invocation in two forms:**
  - Direct flags: `dosforge grow --target VHD --new-size 2G --boot-mode msdos622 [--add-from SRC=DEST ...]`
  - JSON manifest: `dosforge grow --manifest plan.json`
- **Full input validation:**
  - Boot mode must be one of `compaq331` / `msdos622` / `msdos71` / `freedos` (every other mode is either FAT12-capped at 32 MiB or carries quirks that don't justify supporting grow).
  - Target VHD must exist and carry a valid `conectix` fixed-VHD footer.
  - `new_size_bytes` must be strictly larger than the current data area.
  - New size must respect the chosen filesystem's hard cap (FAT16 ≤ 2 GiB, FAT32 ≤ 2 TiB).
  - Each staging source must exist and be a directory.
  - Each staging dest must be an absolute DOS path (`C:\\GAMES`, `\\FOO`, etc.).
- **`GrowManifest` Python dataclass** (`dosforge.grow`) with `to_dict()` and `load_manifest_from_dict()` / `load_manifest_from_json()` round-trip.
- **Schema versioning** (`MANIFEST_SCHEMA_VERSION = 1`) — manifests with mismatched versions are rejected, no silent upgrades.

### What does NOT work yet

Calling `grow_vhd(manifest)` after validation raises
`NotImplementedError` with a clear preview message. The CLI catches
this and surfaces a friendly `"dosforge grow (PREVIEW): ..."` line
plus exit code 2.

### Manifest schema (v1)

```json
{
  "schema_version": 1,
  "target_vhd": "C:/dosgames/exodos.vhd",
  "new_size_bytes": 2147483648,
  "boot_mode": "msdos622",
  "staging_sources": [
    {"src": "/tmp/exodos-staging/games", "dest": "C:\\GAMES"}
  ],
  "boot_probe": true,
  "keep_backup": true
}
```

`new_size_bytes` also accepts human-friendly strings (`"2G"`,
`"512M"`) which are run through `dosforge.size.parse_size`.

### Planned implementation pipeline

When `grow_vhd` lands fully, it will:

1. Snapshot the old VHD: VBR bytes, MBR boot code, file list +
   attributes (`+s` / `+h` / `+r`), volume label, serial number,
   plus `IO.SYS` / `IBMBIO.COM` bytes verbatim.
2. Build a new VHD container at the requested size with the same
   boot-mode profile.
3. `mformat` the new partition at the **same cluster size** as the
   old (refuses grow if the new size would force a different cluster
   band — that requires `dosforge create`).
4. Restore the old VBR over the new partition's reserved area, with
   only `BPB total_sectors_32` / `sectors_per_fat` updated.
5. mcopy hidden system files FIRST (preserves the cluster-2
   contiguity requirement that MSDOS622 and COMPAQ331 still enforce).
6. mcopy everything else recursively with `mattrib` to restore
   attributes.
7. mcopy the new staging sources.
8. Optional headless QEMU boot probe (toggle with `--no-boot-probe`).
9. Atomic swap (`old.vhd` → `old.vhd.bak`, `new.vhd` → `old.vhd`)
   unless `--no-keep-backup`.
