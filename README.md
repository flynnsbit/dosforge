# vhdmaker

`vhdmaker` is a Python + Textual TUI for Omarchy Linux that creates fixed-size VHD files, formats them with FAT16/FAT32, mounts/unmounts them via NBD, and opens mounted paths in your GUI file manager.

## Status

This repository is a fresh implementation and currently targets Linux hosts with:

- `qemu-img`
- `qemu-nbd`
- `parted`
- `partprobe`
- `mkfs.fat`
- `mount` / `umount`
- `modprobe` (kmod)
- `sudo`
- `xdg-open`

Bootable preparation also requires:

- `mcopy`
- `dd`
- syslinux MBR binary (for example `/usr/lib/syslinux/bios/mbr.bin`)

## Install

```bash
python -m pip install -e .
```

## Run

```bash
vhdmaker
```

The app runs unprivileged and uses `sudo` only for disk operations (connect, partition, format, mount, unmount, disconnect).
Press `q` in the TUI to quit.

When launching the TUI (`vhdmaker` or `vhdmaker tui`), the app now performs a startup sudo-auth check (`sudo -v`) before loading the interface, so password entry happens up front instead of during actions.
It also verifies that runtime non-interactive sudo is usable; if not, launch fails before the UI with remediation guidance.

After startup auth succeeds, runtime disk commands continue using non-interactive sudo calls.

In the TUI, use **Fetch latest FreeDOS into ./freedos** to download and extract FreeDOS assets into a `freedos/` folder in the current working directory. The fetch flow now includes:

- boot files (`KERNEL.SYS`, `COMMAND.COM`, etc.),
- `BOOTSECT_FAT16.BIN`,
- `BOOTSECT_FAT32.BIN` (generated by `mkfs.fat`),
- and a populated `FDOS/` tree (userspace tools/packages) for copying onto created VHDs.

In the create panel, defaults are now **FreeDOS bootable** + **Auto-download FreeDOS image**. Selecting a `.vhd` in the browser also auto-fills create path and create size from the selected file.

When available, the FAT32 boot sector is sourced from a local known-good FreeDOS FAT32 `.vhd` (for example a working shareware/reference disk in the launch directory) before falling back to generic generation.

## CLI quick examples

```bash
# Check dependencies
vhdmaker check-deps

# Check sudo / privilege readiness
vhdmaker sudo-check

# Create a fixed-size FAT16 VHD
vhdmaker create --path ~/vhd/demo.vhd --size 512M --format fat16

# Mount and open in GUI file manager
vhdmaker mount --path ~/vhd/demo.vhd --open

# Unmount
vhdmaker unmount --mount-point ~/.local/state/vhdmaker/mounts/demo-xxxxxxxx
```

## Sudo setup and behavior

- TUI startup prompts for sudo credentials once (`sudo -v`) before UI load.
- CLI create/mount/unmount flows still rely on non-interactive sudo during command execution.
- If you prefer not to rely on cached sudo credentials, configure a scoped `NOPASSWD` policy for only the required commands.

Example sudoers snippet (edit with `visudo` and adjust paths for your distro):

```sudoers
Cmnd_Alias VHDMAKER_CMDS = /usr/bin/qemu-nbd, /usr/sbin/parted, /usr/sbin/partprobe, /usr/sbin/mkfs.fat, /usr/bin/mount, /usr/bin/umount, /usr/sbin/modprobe, /usr/bin/dd, /usr/bin/mcopy, /usr/bin/mattrib
youruser ALL=(root) NOPASSWD: VHDMAKER_CMDS
```

Use the diagnostics command to verify your host configuration:

```bash
vhdmaker sudo-check
```

## Bootable image modes

`vhdmaker` supports two boot-prep modes:

1. **FreeDOS bootable**
2. **MS-DOS 7.1 bootable** (supports FAT16 and FAT32)

In both modes, the app writes boot code from a boot-sector template and copies system files into the target filesystem.
For hard-disk bootability, it also marks partition 1 active and writes MBR boot code (from syslinux `mbr.bin`) to the disk.

### FreeDOS assets

FreeDOS mode supports:

- **Local assets path** (`--boot-assets-path`), either:
  - a directory containing:
    - `KERNEL.SYS`
    - `COMMAND.COM`
    - `BOOTSECT_FAT16.BIN` or `BOOTSECT.BIN` for FAT16
    - optional `MBR_FAT16.BIN` or `MBR.BIN` (440-byte boot code) for FAT16 MBR install
    - `BOOTSECT_FAT32.BIN` or `BOOTSECT.BIN` for FAT32
  - or a `.img` file with FreeDOS system files (FAT16-compatible boot template extraction)
- **Auto-download** (`--freedos-source auto`), which downloads a default FreeDOS boot image and extracts:
  - `KERNEL.SYS`
  - `COMMAND.COM`
  - a FAT16 boot template
  - FreeDOS core packages (`kernel` + `freecom`) into `FDOS/` so `FDOS\BIN` command/kernel binaries are available and preferred for HDD boot

When using the TUI fetch button, `FDOS/` userspace content is also downloaded/extracted so it can be copied to `\FDOS` on bootable VHD creation when local assets are used.

The fetch flow also normalizes FreeDOS startup scripts for HDD boot:

- `CONFIG.SYS` uses `SHELL=C:\COMMAND.COM ...` instead of `A:\...`,
- startup-disabling shell switches (`/D` and forced `/K ...`) are removed so AUTOEXEC startup is not skipped,
- minimal floppy-style `AUTOEXEC.BAT` is expanded with HDD-safe `PATH` / `PROMPT` defaults.
- startup aliases are generated so both `CONFIG.SYS` / `FDCONFIG.SYS` and `AUTOEXEC.BAT` / `FDAUTO.BAT` are available.
- for FAT16 create flow on fixed VHDs, BPB geometry (`sectors/track`, `heads`) is patched from the VHD footer CHS values to avoid early boot hangs on strict emulators.
- for FAT16 create flow, if a local installer-style FreeDOS FAT16 `.vhd` is found (current directory, target directory parent, or assets parent), its MBR+VBR boot records are preferred over floppy-derived templates and cached for future FAT16 builds.
- if no local reference exists, `vhdmaker` falls back to built-in installer-style FAT16 FreeDOS MBR/VBR records, so another VHD is not required at runtime.

> Note: Auto-download currently supports FAT16-style boot templates. For FAT32 FreeDOS boot mode, use a local asset directory with `BOOTSECT_FAT32.BIN`.

### MS-DOS 7.1 assets

MS-DOS 7.1 mode supports either of these local asset layouts:

1. Direct extracted files:
   - `IO.SYS`
   - `MSDOS.SYS`
   - `COMMAND.COM`
   - `HIMEM.SYS`
   - `IFSHLP.SYS`
   - `BOOTSECT_FAT16.BIN` or `BOOTSECT.BIN` for FAT16
   - `BOOTSECT_FAT32.BIN` or `BOOTSECT.BIN` for FAT32
2. Install-disk images in the folder (for example `disk01.img`, `disk02.img`):
   - `vhdmaker` reads `DOS71_1S.PAK` from the images,
   - extracts `IO.SYS`, `MSDOS.SYS`, `COMMAND.COM`, `HIMEM.SYS`, and `IFSHLP.SYS`,
   - derives the needed boot sector template (`BOOTSECT_FAT16.BIN` or `BOOTSECT_FAT32.BIN`) from embedded MS-DOS boot code (`SYS.COM`/`FORMAT.COM`).

MS-DOS 7.1 mode also supports install profiles:

- `minimal` (default): bootable core files only (`IO.SYS`, `MSDOS.SYS`, `COMMAND.COM`).
- `full`: copies the DOS payload into `\DOS` (equivalent to a fuller `C:\DOS` command/tools tree from install media).
- both profiles now place default `CONFIG.SYS` and `AUTOEXEC.BAT` in the root (`C:\`) when not explicitly supplied.
- startup files are normalized to installer-style DOS defaults:
  - `AUTOEXEC.BAT` keeps `PATH=C:\DOS;..;.` at the top (after `@ECHO OFF`),
  - `CONFIG.SYS` appends `SET PATH=C:\DOS;..;.` and rewrites `DEVICE`/`DEVICEHIGH` entries to `C:\DOS\...` when they reference DOS components.

Use `--msdos-install-profile minimal|full` in CLI, or select the MS-DOS profile in TUI.

The app does not bundle proprietary MS-DOS files.

## Compatibility guardrails

- FAT16 VHD size range: **16 MiB to 2 GiB**
- FAT32 minimum VHD size: **64 MiB**
- FAT32 maximum VHD size: **2 TiB**
- MS-DOS 7.1 boot mode supports FAT16 and FAT32

## State and mounts

`vhdmaker` stores runtime state in:

- `~/.local/state/vhdmaker/state.json`
- mount points under `~/.local/state/vhdmaker/mounts/`

Use `vhdmaker list-mounts` to view tracked active mounts.

## NBD troubleshooting

If mount fails with `No /dev/nbd* devices are available on this host`:

1. `vhdmaker` now attempts to load the kernel module automatically using `sudo modprobe nbd max_part=16`.
2. If your kernel does not expose NBD devices after that, run:
   - `sudo modprobe nbd nbds_max=16 max_part=16`
3. Confirm the device exists:
   - `ls /dev/nbd0`
